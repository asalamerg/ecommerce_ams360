# الدفع الإلكتروني

البنية جاهزة وتعمل ببوابة اختبار (`fake`). عند وصول بيانات الـ API من مزوّد الدفع، يكفي كتابة صنف واحد للبوابة وتسجيله. هذه الوثيقة موجّهة للمطوّر الذي سيربط المزوّد.

## مسار الدفع

1. يختار العميل «ادفع بالبطاقة» في السلة. ينشئ `PlaceOrder` الطلب بحالة `pending` ودفع `pending`، ويُحجز المخزون.
2. ينشئ `StartPayment` محاولة دفع في جدول `payments` بمبلغ الطلب المحفوظ ومفتاح `idempotency_key` ورمز عودة سرّي، ثم يطلب من البوابة صفحة الدفع.
3. يدفع العميل في صفحة المزوّد. **أرقام البطاقات لا تمر بخادمنا أبدًا** (نطاق PCI SAQ-A).
4. يرسل المزوّد إشعارًا موقّعًا إلى `POST /payments/webhook/{gateway}`. يعالجه `HandlePaymentWebhook`.
5. يعود العميل إلى `/payments/return/{id}/{token}`. لا يُصدَّق أي شيء في هذا الطلب، فالخادم يسأل المزوّد مباشرة عبر `status()`.
6. يطبّق `ApplyGatewayStatus` الجواب في مكان واحد: الطلب مدفوع، فينتقل إلى «قيد المعالجة»، ويُنبَّه الموظفون ويُراسَل العميل.
7. الطلب غير المدفوع خلال `PAYMENT_PENDING_MINUTES` دقيقة (30 افتراضيًا) يُلغى ويعود مخزونه، بعد سؤال المزوّد مرة أخيرة.

## ضمانات الأمان

| الخطر | الحماية |
|---|---|
| تزوير المبلغ من المتصفح | المبلغ من الطلب المحفوظ فقط. يجب أن يطابق ما يبلّغ به المزوّد المبلغَ والعملة بالضبط، وإلا تصبح الحالة «مراجعة» ويُنبَّه المالك. |
| إشعار مزوّر | توقيع HMAC على الجسم الخام، ومقارنة بزمن ثابت (`hash_equals`)، ومهلة 5 دقائق. |
| إعادة إرسال إشعار قديم | معرّف الحدث فريد في `payment_webhook_events`، والتكرار لا يغيّر شيئًا. |
| تسرّب سرّ التوقيع | `PAYMENT_VERIFY_WITH_API=true` (افتراضي): تُقرأ الحالة من API المزوّد قبل التطبيق، فالإشعار وحده لا يكفي. |
| تعديل رابط العودة (`?status=paid`) | يُتجاهل. الدفع يُعرف برمز سرّي مخزّن كبصمة SHA-256، والحالة من المزوّد. |
| خصم مرتين | `idempotency_key` يُرسل مع كل طلب إنشاء، ولا يبقى إلا محاولة واحدة مفتوحة لكل طلب. |
| دفع بعد انتهاء المهلة | المحاولة الملغاة تُتجاهل. دفعة ثانية لطلب مدفوع تصبح «مراجعة» ليُسترد مبلغها. |
| إعادة توجيه إلى موقع آخر | يُرفض رابط صفحة الدفع إن لم يكن على نطاقات `browser_origins` للمزوّد. |
| تعديل الموظف «مدفوع» يدويًا | ممنوع لطلبات البوابة. الحالة يغيّرها تأكيد المزوّد فقط. |
| استرداد غير مصرّح به | للمالك والمدير فقط، بعد تأكيد كلمة المرور، وعبر API المزوّد. |
| بوابة الاختبار في الإنتاج | `PaymentManager` يرفضها (`forTestingOnly()`) مهما كانت الإعدادات. |
| CSRF على الإشعارات | مسار الإشعار مستثنى من CSRF لأنه موقّع، ومحدود بـ 120 طلبًا في الدقيقة، وحجمه الأقصى 64 كيلوبايت. |

## إضافة المزوّد الحقيقي

1. أنشئ `app/Payments/Gateways/{Name}Gateway.php` ينفّذ `PaymentGateway`، واتخذ `FakeGateway` نموذجًا. القواعد:
   - `start()`: أرسل `minorAmount()` (بالأغورة إن طلب المزوّد ذلك) و`idempotency_key` ورابطي العودة والإشعار. أعِد رابط صفحة الدفع ومرجع المزوّد.
   - `parseWebhook()`: تحقق من التوقيع **قبل** قراءة أي حقل. إن كان المزوّد يوقّع بصيغة `t=…,v1=…` فاستخدم `HmacSignature::verify()`، وإلا فاكتب تحققًا بالقواعد نفسها: الجسم الخام، و`hash_equals`، ومهلة زمنية. أطلق `InvalidWebhook` عند الفشل.
   - `status()` و`refund()`: طلب خادم-إلى-خادم بمفتاح الـ API، وحوّل الجواب إلى `GatewayStatus`.
   - `browserOrigins()`: نطاقات صفحات الدفع، مثل `https://secure.provider.co.il`.
   - `forTestingOnly()`: أعِد `false`.
2. سجّله في `PaymentManager::GATEWAYS` وأضف إعداداته في `config/payments.php`. الأسرار تُقرأ من `.env` فقط.
3. أضف `webhook_ips` إن نشر المزوّد عناوين إشعاراته.
4. في `.env` على الخادم: `PAYMENT_GATEWAY={name}` والمفاتيح. سجّل في لوحة المزوّد رابط الإشعار `https://example.com/payments/webhook/{name}`.
5. اكتب اختبارات بنمط `tests/Feature/Payments/OnlinePaymentTest.php` مع `Http::fake()` لردود المزوّد.
6. جرّب في بيئة الاختبار (sandbox) لدى المزوّد: دفع ناجح، ورفض، وإغلاق الصفحة دون دفع، واسترداد.

## التجربة محليًا

ضع `PAYMENT_GATEWAY=fake` في `.env` المحلي. في السلة يظهر «ادفع بالبطاقة الآن»، فتنقلك إلى صفحة اختبار فيها «Approve» و«Decline». القرار يمر عبر الإشعار الموقّع نفسه الذي سيرسله المزوّد الحقيقي.
